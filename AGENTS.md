## ЧАСТЬ I. Общие принципы (Языконезависимые)

### 1. Архитектура и границы (SOLID / Clean Architecture)
- **Изоляция слоев:** Разделяйте Domain (сущности/чистая логика), Application/UseCases (сценарии) и Infrastructure (БД, сетевые клиенты, файловая система, внешние API).
- **Инверсия зависимостей (DIP):** Внутренние слои никогда не импортируют и не зависят от деталей внешних слоев. Внешние зависимости передаются через абстракции (интерфейсы/трейты/протоколы).
- **Single Responsibility (SRP):** Один модуль, структура или класс отвечают за одну задачу. Если функция делает расчет и одновременно пишет в лог/БД — разделите их.
- **Минимальный скоуп правок:** Запрещено проводить спонтанные рефакторинги несвязанных модулей. Изменяйте только файлы в рамках поставленной задачи.

### 2. KISS & DRY
- **Простота превыше магии:** Предпочитайте явный, линейный и легко читаемый код сложным абстракциям, метапрограммированию и фабрикам фабрик.
- **Guard Clauses:** Избегайте глубокой вложенности (`if/else`). Используйте ранний возврат (`return`, `?`, `continue`).
- **Истинный DRY:** Устраняйте дублирование бизнес-правил, но не объединяйте разные по смыслу сущности только из-за временного совпадения набора их полей.

### 3. Отказоустойчивость и безопасность
- **Fail Gracefully:** Ошибка парсинга или отказ единичного внешнего запроса не должны крашить процесс сервиса.
- **Таймауты и I/O:** Любая операция ввода-вывода (сеть, диск, очереди) обязана иметь сконфигурированный таймаут.
- **Защита данных:** Запрещено выводить в логи или возвращать наружу пароли, секреты, токены авторизации и персональные данные (PII).

## ЧАСТЬ II. Специфика разработки на Rust

### 1. Обработка ошибок и паники
- **Категорический запрет на неконтролируемые паники:**
  - В продакшн-коде запрещены `.unwrap()`. 
  - `.expect("invariant description")` допустим **только** при наличии железного инварианта, доказанного кодом выше (например, валидация регулярного выражения при старте приложения).
  - Никаких явных вызовов `panic!()`, `unreachable!()` или `todo!()` в рабочем коде.
- **Типизация ошибок:**
  - Для библиотечного/доменного кода используйте строгие типизированные перечисления через `thiserror`.
  - Для приложений верхнего уровня (CLI, бинарники, main) допустим `thiserror`.
  - Обогащайте ошибки контекстом (`.context("failed to fetch user config")`).
- **Оператор `?`:** Активно используйте ранний проброс ошибок вместо громоздких конструкций `match`.
- **Старайтесь использовать самые последние доступные стабильные версии крейтов при написании проекта**.

### 2. Память, владение и производительность
- **Минимизация клонирования:** Не решайте проблемы borrow checker слепым вызовом `.clone()`. Используйте ссылки (`&T`, `&str`, `&[T]`) и срезы там, где владение не требуется.
- **Borrow Checker idiomatic design:** Проектируйте структуры так, чтобы минимизировать циклы ссылок. Избегайте без крайней необходимости использования `Rc<RefCell<T>>` или небезопасных сырых указателей.
- **Использование `unsafe`:** Строго запрещено, если нет явного требования задачи с математическим доказательством необходимости и подробным блоком `// SAFETY: ...`.
- **Семантика типов (Newtype Pattern):** Оборачивайте сырые идентификаторы и критические значения в типы (`struct UserId(Uuid)`), чтобы исключить случайную путаницу аргументов в функциях.

### 3. Асинхронность и многопоточность
- **Tokio / Async best practices:**
  - Никогда не блокируйте runtime! Тяжелые вычисления или синхронный I/O выполняйте исключительно в `tokio::task::spawn_blocking`.
  - Корректно обрабатывайте отмену задач (`tokio::select!` с ветками завершения/shutdown).
  - Для разделяемого изменяемого состояния в многопоточке используйте `Arc<tokio::sync::Mutex<T>>` только при удержании лока через `await`. В остальных случаях предпочитайте `std::sync::Mutex` или каналы передачи сообщений (`tokio::sync::mpsc`).

### 4. Тестирование и экосистема
- **Интеграция тестов:** Модульные тесты пишите в том же файле в модуле `#[cfg(test)] mod tests { ... }`.
- **Проверки перед коммитом:** Код обязан компилироваться без предупреждений:
  ```bash
  cargo clippy --all-targets --all-features -- -D warnings
  cargo test
  cargo fmt --check
  ```

## ЧАСТЬ III. Специфика разработки на Python

### 1. Типизация и статический анализ

* **100% Type Hints:** Все параметры функций, возвращаемые значения и поля классов должны быть строго типизированы (`typing`, Python 3.10+ синтаксис `X | Y`, `list[str]`).
* **Запрет `Any`:** Использование `Any` запрещено без веской причины и письменного комментария. Используйте `TypeVar`, `Generic` или `Protocol`.
* **Интерфейсы через `Protocol`:** Для инверсии зависимостей и утиной типизации используйте `typing.Protocol` (структурное подтипирование), а не тяжелое множественное наследование.
* **Валидация данных:** Для данных, поступающих извне (API, конфиги, окружение), используйте `Pydantic v2` или `dataclasses` (с явной валидацией).

### 2. Обработка исключений и надежность

* **Никаких `bare except`:**
* Запрещено: `except:`, `except Exception: pass`.
* Перехватывайте только конкретные ожидаемые исключения (`except KeyError:`, `except httpx.RequestError:`).


* **Своя иерархия исключений:** Модуль/библиотека должны иметь базовое доменное исключение (например, `class DomainError(Exception): pass`) и наследоваться от него.
* **Контекстные менеджеры:** Любые ресурсы (файлы, сетевые сессии, коннекты к БД, блокировки) обязаны управляться через `with` или `async with`.
* **None-safety:** Не полагайтесь на неявную истинность (`if not val:`). Если значение может быть `None`, делайте явную проверку: `if val is None:`.

### 3. Чистота кода и Idiomatic Python

* **Избегайте скрытого состояния:** Никаких изменяемых значений по умолчанию в аргументах функций (`def add(item, items=[]):` — строго запрещено; используйте `items: list | None = None`).
* **Сложность функций:** Избегайте спагетти из list/dict comprehension. Если comprehension занимает больше двух строк или содержит вложенные условия — перепишите на явный цикл или вынесите в генератор.
* **Работа с путями:** Используйте `pathlib.Path` вместо строковых операций с `os.path`.

### 4. Асинхронность (Asyncio)

* **Изоляция блокировок:** Не вызывайте синхронный I/O (`requests`, `time.sleep`, стандартное чтение файлов) внутри `async def`. Используйте `httpx`, `aiofiles` или `asyncio.to_thread()`.
* **Управление задачами:** Используйте `asyncio.TaskGroup` (Python 3.11+) или явно отслеживайте и отменяйте фоновые задачи (`task.cancel()`), чтобы избегать «зависших» корутин.

### 5. Тестирование и линтинг

* **Pytest conventions:** Используйте `pytest`. Тестовые фикстуры выносите в `conftest.py`, параметризацию делайте через `@pytest.mark.parametrize`.
* **Изоляция:** Запрещены сетевые запросы во время прогона юнит-тестов (используйте моки, `pytest-mock`, `respx` или `unittest.mock`).
* **Проверки перед коммитом:**
  ```bash
  ruff check .
  ruff format --check .
  mypy --strict .
  pytest -v
  ```
